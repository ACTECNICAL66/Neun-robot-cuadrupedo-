INTRODUCCIÓN: ¿QUÉ ES ESTE PROGRAMA?
====================================================================

NEUN-APP.py es el "cerebro" de un robot araña. Corre en una PC y
tiene 3 trabajos principales:

  1. Servir una PÁGINA WEB (interfaz gráfica) para controlar el robot
  2. Conectarse por WiFi al ESP32-S3 (el microcontrolador del robot)
  3. SIMULAR datos cuando el robot real no está conectado

La comunicación es así:

  [TU PC - Flask]  <---WiFi--->  [ESP32-S3 del robot]
       |                               |
  localhost:5000                   192.168.4.1
  (面板 web táctil)          (datos reales de sensores)

Si el ESP32 no responde → el programa inventa datos (MODO DEMO).
Si el ESP32 responde   → usa datos reales (MODO REAL).

====================================================================

  @dataclass
  class Config:
      esp32_ip: str = "192.168.4.1"
      esp32_port: int = 80
      ...

  Una @dataclass es UNA CLASE SIMPLE que solo guarda datos. Es como
  un formulario con campos y valores por defecto.

  ¿Por qué usar una clase para la configuración?
  - Todos los valores están en un solo lugar
  - Fáciles de cambiar
  - Si necesitas cambiar la IP del ESP32, solo cambias esta línea

  @property
  def esp32_base_url(self) -> str:
      return f"http://{self.esp32_ip}:{self.esp32_port}"

  @property crea un "método que parece una variable". Cuando escribes
  config.esp32_base_url, calcula la URL automáticamente:
  -> "http://192.168.4.1:80"

  Valores importantes:
  - poll_interval_ms = 500:  El frontend web pregunta cada 0.5 segundos
  - connection_timeout = 1.0:  Espera 1 segundo a que el ESP32 responda
  - max_logs = 100:  Solo guarda los últimos 100 mensajes de log
  - max_backoff = 30:  Si el ESP32 no responde, espera hasta 30 segundos

  Símil:  Es como la caja de herramientas con las instrucciones de
          "cada cuánto hacer cada cosa".

PARTE 4: ESTADO DE SENSORES (SensorState, líneas 62-97)
====================================================================

  @dataclass
  class SensorState:
      ultrasonic: dict = field(default_factory=lambda: {...})
      imu: dict = field(default_factory=lambda: {...})
      ir: dict = field(...)
      dht: dict = field(...)
      leds: dict = field(...)
      servos: dict = field(...)

  Aquí se define el estado de CADA SENSOR del robot. Cada sensor es
  un diccionario (dict), que es como una "caja con etiquetas".

  Ejemplo del sensor ultrasónico (radar de distancia):
  {
      "online": True,      ->  ¿Está funcionando?
      "value": 42.5,       ->  Distancia medida: 42.5 cm
      "unit": "cm",        ->  Unidad: centímetros
      "name": "Radar HC-SR04",  ->  Nombre para mostrar
      "pin": "GPIO10/11"   ->  Pines físicos donde se conecta
  }

  Sensor IMU (MPU6050): mide inclinación (pitch, roll, yaw),
  aceleración (ax, ay, az), y velocidad angular (gx, gy, gz).

  Sensor DHT22: temperatura y humedad del ambiente.

  ¿Por qué field(default_factory=lambda: {...})?
  - Si usáramos {} directamente, TODAS las instancias compartirían
    el mismo diccionario (un bug común en Python).
  - default_factory=lambda: {...} crea un diccionario NUEVO cada vez.

  to_dict() junta todos los sensores en un solo diccionario grande
  para enviarlo como JSON.

  Símil:  Es como el panel de instrumentos de un auto: cada sensor
          es un indicador (velocidad, temperatura, etc.).

PARTE 7: SensorSimulator — MODO DEMO (líneas 192-231)
====================================================================

  class SensorSimulator:
      def __init__(self, state):
          self._state = state   # Guarda referencia al estado global

      def update(self):
          if self._state.connected:
              return  # Si hay ESP32 real, NO simular

  Lógica: cada 0.4 segundos (desde el hilo), este método se ejecuta.
  Si el ESP32 real está conectado, no hace NADA. Si no, inventa datos.

  Cómo simula cada sensor:

  * ULTRASONIDO (distancia):
    Valor actual + un número al azar entre -8 y +8
    Ej: si estaba en 42.5cm, puede ir a 35.2cm o 49.8cm
    Luego lo limita entre 5 y 400 (rango real del sensor)

  * IR (infrarrojo):
    Valor actual + un entero al azar entre -60 y +60
    Limitado entre 0 y 1023

  * DHT22 (temperatura y humedad):
    Temperatura: ±0.3°C (limitado 15-40°C)
    Humedad: ±1.5% (limitado 20-90%)

  * IMU (acelerómetro/giroscopio):
    Pitch y roll: ±3° (limitado ±45°)
    Yaw: gira 0-360° continuamente
    Giroscopio: ruido aleatorio ±200

  * BATERÍA:
    Disminuye 0.02% cada ciclo (simula descarga lenta)

  * FALLAS ALEATORIAS:
    0.5% de probabilidad por ciclo → un sensor se desconecta
    0.8% de probabilidad por ciclo → un sensor desconectado se reconecta

  Estas probabilidades hacen que las fallas sean IMPREVISIBLES pero
  no demasiado frecuentes. Es realista.

  Símil:  SensorSimulator es como un simulador de vuelo: cuando no
          tienes el avión real, el programa te muestra datos
          inventados pero creíbles.

  def ping(self) -> bool:
      try:

  El try/except captura CUALQUIER error (timeout, conexión rechazada,
  etc.) y devuelve False.

  def fetch_status(self) -> bool:
  Como ping() pero más completo: trae TODOS los datos del ESP32.

PARTE 9: HILOS (THREADS) — COSAS EN PARALELO (líneas 301-338)
====================================================================

  def _sensor_loop():
      while True:              # Bucle INFINITO
          simulator.update()    # Actualiza sensores simulados
          time.sleep(0.4)       # Espera 0.4 segundos

  threading.Thread(target=_sensor_loop, daemon=True).start()

  Un HILO (thread) es como tener UN TRABAJADOR EXTRA que hace una
  tarea mientras el programa principal sigue haciendo otra cosa.

  El sensor loop es un bucle que NUNCA TERMINA (while True). Cada
  0.4 segundos actualiza los sensores. Sin hilos, esto BLOQUEARÍA
  el programa y Flask no podría responder peticiones web.

  daemon=True significa: "si el programa principal termina, mátame
  también". Así no quedan procesos zombies.

  def _connection_monitor():
      attempts = 0
      while True:
          if esp32.ping():        # ¿El ESP32 responde?
              esp32.fetch_status()  # Trae datos
              attempts = 0          # Resetea contador
              time.sleep(2)
          else:
              attempts += 1
              espera = min(2 * (2 ** (attempts // 10)), 30)
              time.sleep(espera)

  BACKOFF EXPONENCIAL:
  - Intento 1-10:  espera 2 segundos
  - Intento 11-20: espera 4 segundos (2^1)
  - Intento 21-30: espera 8 segundos (2^2)
  - ...hasta máximo 30 segundos

  ¿Por qué? Para no saturar la red cuando el ESP32 está apagado.
  Cuando vuelve a responder, se resetea a 2 segundos.

  Este hilo NO arranca solo. Arranca cuando el usuario hace clic
  en "Conectar" desde la interfaz web.

  Símil:  Los hilos son como tener ayudantes:
          - Hilo 1: Actualiza sensores cada 0.4s
          - Hilo 2: Vigila la conexión con el ESP32
          - Hilo principal (Flask): Atiende la página web

PARTE 10: CommandDispatcher — EL ENRUTADOR DE ÓRDENES (líneas 344-416)
====================================================================

  class CommandDispatcher:
      def __init__(self, state, esp32):
          self._handlers = {
              "mode":      self._handle_mode,
              "move":      self._handle_move,
              "aux":       self._handle_aux,
              "speed":     self._handle_speed,
              "emergency": self._handle_emergency,
              "stabilize": self._handle_stabilize,
              "servo":     self._handle_servo,
              "servo_adv": self._handle_servo_adv,
              "terminal":  self._handle_terminal,
          }

  Es un DICCIONARIO que mapea NOMBRES DE COMANDO a FUNCIONES.
  Cuando llega un comando "mode", busca la función _handle_mode
  y la ejecuta.

  def dispatch(self, cmd, value=None):
      # 1. Si hay ESP32, reenviar el comando al robot real
      if self._state.connected and cmd != "terminal":
          self._esp32.send_command(cmd, value)

      # 2. Ejecutar handler local SIEMPRE
      handler = self._handlers.get(cmd)
      if handler:
          handler(value)

      return {"status": "ok", "esp32_forwarded": True/False}

  PRIMERO reenvía al ESP32 (si está conectado), LUEGO ejecuta el
  handler local. El handler local actualiza el estado para que la
  UI se entere del cambio.

  Handlers específicos:

  _handle_mode(value):
      state.mode = value   ("Stand", "Caminar", "Trotar"...)

  _handle_move(value):
      Solo loguea el movimiento

  _handle_speed(value):
      state.speed = int(value)

  _handle_emergency(value):
      state.emergency_stop = True/False
      Loguea en rojo si es emergencia

  _handle_servo(value):
      Espera un dict: {"leg": 0, "joint": 1, "angle": 90}
      state.servos[leg][joint] = angle

  _handle_servo_adv(value):
      Espera un dict: {"channel": 5, "angle": 90}
      channel // 3 = pata, channel % 3 = articulación
      Ej: canal 5 -> pata 1, articulación 2

  Símil:  Es como un CENTRAL TELEFÓNICO: recibe una llamada (comando)
          y la redirige al departamento correcto (handler).

  _CHAT_RESPONSES = {
      "hola": "¡Hola! Soy el asistente de la Araña Robot...",

      "sensor": "Todos los sensores están online...",

      "parar": "Deteniendo movimiento...",
      "stop": "Deteniendo movimiento...",
      "emergency": "Activando Emergency Stop...",
      "velocidad": None,  # Se resuelve dinámicamente
  }

  def process_chat_message(msg):
      state.add_chat("user", msg)  # Guarda mensaje del usuario

      for keyword, response in _CHAT_RESPONSES.items():
          if keyword in msg.lower():
              # Si la palabra clave está en el mensaje...

              if keyword == "bateria":
                  resp = f"La batería está en {state.battery:.0f}%."
              elif keyword == "velocidad":
                  resp = f"La velocidad actual es {state.speed}%."
              elif keyword in ("parar", "stop"):
                  resp = response
                  state.log("Stop por chat", "warn")
              elif keyword == "emergency":
                  resp = response
                  state.emergency_stop = True
              else:
                  resp = response

              state.add_chat("ai", resp)
              return resp

      # Si ninguna palabra clave coincide:
      resp = "Puedes preguntarme sobre modos, sensores..."
      state.add_chat("ai", resp)
      return resp

  NO usa inteligencia artificial real. Es un simple "match por
  palabra clave". Si el usuario escribe "dame la batería", contiene
  "bateria" → responde con el nivel actual.

  Algunos comandos además de responder, EJECUTAN ACCIONES:
  - "parar" / "stop": registra una parada en los logs
  - "emergency": activa la parada de emergencia real

  Símil:  Es como un contestador automático que reconoce palabras
          clave y responde algo pre-escrito.

  Endpoints de la API:

  1. GET /api/status
     -> Devuelve TODO el estado del robot (sensors, battery, mode...)
     -> El frontend lo llama cada 500ms para actualizar la pantalla

  2. GET /api/esp32_status
     -> Solo conexión: {"connected": True, "esp32_ip": "...", ...}
     -> Para el indicador LED de conexión en la UI

  3. GET /api/connect_esp32
     -> Arranca el monitor de conexión
     -> Hace ping + fetch_status
     -> Si funciona: {"success": True, "message": "Conectado"}
     -> Si no:      {"success": False, "message": "No responde"}

  4. GET /api/disconnect
     -> Simplemente marca connected = False

  5. POST /api/command
     -> Recibe: {"cmd": "mode", "value": "Caminar"}
     -> Lo manda al CommandDispatcher
     -> Devuelve: {"status": "ok", "esp32_forwarded": True}

  6. POST /api/chat
     -> Recibe: {"message": "hola"}
     -> Procesa con process_chat_message()
     -> Devuelve: {"response": "¡Hola!..."}

  Símil:  Flask es como un RESTAURANTE:
          - El menú son las rutas (/api/status, /api/command...)
          - Los mozos son Flask que llevan las peticiones
          - La cocina es la lógica que procesa cada pedido
          - La respuesta JSON es el plato terminado

CONCEPTOS CLAVE PARA PRINCIPIANTES
====================================================================

  1. ¿Qué es un DICCIONARIO (dict)?
     Es como una caja con etiquetas. En vez de números (como las
     listas), usa palabras clave para guardar cosas:
       persona = {"nombre": "Juan", "edad": 25}
       print(persona["nombre"])  → "Juan"

  2. ¿Qué es @dataclass?
     Una forma de crear clases que solo guardan datos, sin escribir
     todo el código repetitivo. Python lo genera automáticamente.

  3. ¿Qué es un HILO (thread)?
     Un programa normalmente hace una cosa a la vez. Los hilos
     permiten hacer VARIAS COSAS "AL MISMO TIEMPO".
     Ej: mientras Flask atiende la web, otro hilo actualiza sensores.

  4. ¿Qué es JSON?
     Un formato de texto para intercambiar datos. Es como un
     diccionario de Python pero en texto. Se usa para comunicar
     el frontend (JavaScript) con el backend (Python/Flask).

  5. ¿Qué es una API REST?
     Una forma de comunicación donde:
     - GET = "dame datos"
     - POST = "toma esto y haz algo"
     Las respuestas son en JSON.

  6. ¿Qué es try/except?
     "Intenta hacer esto, y si falla, haz esto otro".
     Evita que el programa se rompa cuando algo sale mal.

  7. ¿Qué es un @property?
     Un método que se llama como si fuera una variable.
     En vez de config.esp32_base_url(), escribes config.esp32_base_url.

  8. ¿Qué significa if __name__ == "__main__"?
     "Solo ejecuta esto si corres este archivo directamente".
     Si importas el archivo desde otro lado, no se ejecuta.
